## Applied camera fix

The tested environment is Windows 11 x64, Ubuntu 24.04.5, WSL 2.7.13 and
usbipd-win 5.3.0. The camera identifies as OV9600 under `gspca_ov519`.

A full kernel and matching module tree were built from the recorded upstream
commit `1bd4ed3d4ada93738eef3fc2a66b674c640dc326` and recovered configuration,
then activated as `6.18.35.2-microsoft-standard-WSL2-orion-nina1`.

The unmodified driver returned complete VGA frames but short SXGA frames.
Skipping startup frames did not fix this. Its OVFX2 path ignored the existing
`frame_rate` module parameter. The [three-line GPL driver patch](../kernel/wsl/ovfx2-frame-rate.patch)
copies that parameter into the OVFX2 device setting. The replacement
`gspca_ov519` module compiled with `-Werror`, matched the active kernel and was
installed with the original module backed up. The kernel image and
`gspca_main` were not replaced by the subsequent module-only build.

The persistent setting is `options gspca_ov519 frame_rate=10`. With this patch
and OV9600, it selects the discrete **7.5 fps at 1280 x 1024** and **15 fps at
640 x 480** modes. It does not mean a 10 fps stream or a measured exposure.
The loaded value was checked after a driver reload. See the
[build, installation and recovery instructions](../kernel/wsl/OVFX2_FRAME_RATE.md)
and [configuration sample](../config/orion-ovfx2.conf).

## Unresolved exposure behaviour

The driver exposes raw exposure values 0..255; there is no validated conversion
to seconds. A later settled-frame check used automatic mode followed by manual
0, 50, 127 and 255. Every saved raw frame was complete. Automatic mean
brightness was about 86 ADU; all four manual means were about 91.6 ADU, with
no clear response across the raw settings.

Illumination was not controlled, so this does not establish a failed sensor or
an exposure calibration. Manual V4L2 readback can reflect cached driver values.
Investigate sensor register behaviour rather than treating readback as proof.
The prior automatic setting and VGA format were restored after the check.

Frame rate, elapsed capture time and a software wait do not establish sensor
integration time. Do not invent a timing profile, substitute raw register
values for seconds, or interpret these noise/brightness checks as scene detail.

## Prepared N.I.N.A. path

`alpaca/orion_alpaca.py` provides an experimental CameraV3 HTTP adapter and an
explicitly named simulator. `alpaca/orion_v4l2.py` verifies the camera identity,
driver, format, ownership and frame size. Physical connection/capture is
deliberately refused without a measured exposure profile. The existing panel
and shell capture path are unchanged.

The intended connection is:

```text
Orion USB -> usbipd -> WSL ov519/V4L2 -> Python Alpaca -> Windows N.I.N.A.
```

N.I.N.A. 3.2.1.3002-rc is installed on the tested PC. Its **Alpaca Camera -
Static IP** option can use HTTP, `127.0.0.1`, port `11111`, device `0`.
WSL-to-Windows localhost transport passed simulator client-library checks;
UDP discovery and the actual GUI capture flow remain unverified. The simulator
launcher produces synthetic data only. See [N.I.N.A. setup](NINA_SETUP.md).

The adapter currently supports 1280 x 1024 BGGR8, bin 1 and even-origin software
subframes. Cooling, gain control, guide output, mechanical shutter and long
exposure emulation are unavailable. Physical integration start timestamps are
not advertised; exposure metadata must remain honest.

## Operating and recovery notes

Use **Launch Orion StarShoot.cmd** for the existing panel. Its own keep-alive
holds the WSL connection while the panel is open. Never run the panel's media
capture, INDIGO/INDI and the Alpaca backend against the camera concurrently.

After WSL restarts, this camera once appeared as a Windows descriptor-error
device. Unplugging only the camera, waiting about ten seconds and reconnecting
restored its identity. Recheck exact VID/PID and current bus ID before attaching;
do not bind an unidentified device or reset a shared hub. The serial mount,
webcam and Bluetooth bindings were not changed.

The separate local handover records rollback backups and evidence paths.
Preserve existing captures and configuration. No further kernel or driver
change is needed just to focus with the working panel.
